Skill for coding agents

OpenCode 1,390 lines CC BY-NC-ND 4.0

Turns work you and a human just did together into a tutorial: volumes, chapters, every element explained, every line written out live with its reason and its consequence.

The problem it solves

Most generated documentation explains finished code. The finished code cannot tell you that the build failed twice because a file was locked, that the obvious approach was wrong, that three attempts were tried before one worked. That information exists only in the history of the work.

This skill keeps the mistakes. A step looks like this:

Why we write this. Electron has no window until the app reports that it finished booting, and whenReady is that report. Anything visual has to wait for it.

What we are writing. Three things. The import brings in the two Electron pieces we need. whenReady().then schedules work for after boot. BrowserWindow creates the window, and we hold it in a variable.

What happens if we leave it out. Without the import, app is undefined and the app dies on startup. Create the window before whenReady and we get ERR_ELECTRON_BEFORE_READY and an immediate exit. Drop the const win and the window flashes for a fraction of a second and disappears.

What comes out

  • an opening that says what is being built and why, before any detail;
  • a contents listing of volumes, chapters and elements;
  • every element answered three times: what it is, why it exists, what breaks without it — concretely, not “it is required”;
  • code written out live in prose, not tabulated;
  • two kinds of errors kept apart: the ones that actually happened, quoted verbatim, and the ones a reader starting from a different machine is about to hit;
  • abandoned approaches, recorded so the reader does not spend the same hour.

Structure

Volume      a major part of the program: a platform, a runtime, a subsystem
  Chapter   a phase with a checkable outcome: "the build produces a signed APK"
    Element a file, an asset, an object, a layer — what breaks without it
      Step  the action, written out, with its reason and its consequence

Install

npx skills add fworkslab/build-with-me@build-with-me -a opencode -g -y

Or copy it yourself — a skill is one file with a YAML header:

~/.config/opencode/skills/build-with-me/SKILL.md

It is not only for code

The structure survives when the project is not a program. Only the vocabulary changes: the element is whatever the reader will come back to when something is broken, and a step is any action named exactly enough to repeat.

ProjectAn element isA step is
Programa filecode
Game on an enginean asset, an actor, a Blueprint, a levela tool call, a console command
Blendera collection, a modifier, a bone, a keyframean exact operation with its setting
Maya, Houdini, ZBrusha node, a subtool, an anchor pointan exact parameter change
Spreadsheet, analysisa sheet, a named range, a formulathe formula, with its cell addresses
Documenta heading level, a section, a styleapplying the named style
Drawinga layer, a pass, a palettea stroke with tool, size, angle

What it will not do

  • Pad a small project. Elements are counted from the machine before any chapter is planned, so a folder holding one file gets one chapter — not two volumes, a contents tree, and eight hundred lines.
  • Invent a past error. If a step went cleanly, it says so. A tutorial with manufactured problems teaches the reader to expect failures that never occur.
  • Invent a history of troubles it never saw. Given a repository someone else built, the structure and reasoning still work because they are deduced from the files. What actually went wrong does not — and the tutorial says plainly which parts are reconstructed from the code rather than from the build.
